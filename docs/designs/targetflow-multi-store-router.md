## Problem Statement

Operate several independently configured Shopify stores that sell the same real product at the same price, while running one Meta ad campaign with one public destination URL. The system must route each visit to an eligible store and continuously steer traffic toward each store’s own daily revenue target without cloaking, redirect loops, or unreliable attribution.

## Demand Evidence

- The founder already operates real Shopify stores and Meta campaigns, not a hypothetical marketplace.
- The present repository already contains a two-store threshold rotator, Shopify webhook verification, and an admin interface; the immediate need is to evolve it into a 10–50+ store business system.
- Concrete desired operating modes are target balancing, equal rotation, fill-then-skip, priority weighting, and immediate per-store manual controls.

## Status Quo

Today the app picks between two stores, rotates after a paid/authorized-order threshold, and records basic redirects and orders. It cannot assign independently configured targets to many stores, identify a specific click across different storefront domains, model refunds or delayed financial state, calculate a credible real-time allocation, or provide the operational controls needed for a production campaign.

## Target User & Narrowest Wedge

The first user is the operator of these stores. The narrowest valuable release is a control room that routes one campaign link across 3–10 active stores, applies each store’s daily revenue target, records attributable Shopify orders, shows progress live, and allows an operator to pause or cap a store safely.

## Constraints

- Every destination storefront serves the same product and price. Store configuration, Shopify installation/webhook credentials, targets, limits, and status are separate per store.
- The one advertised URL is stable, transparent, and gives all ordinary visitors the same type of product experience. No user-agent, reviewer, crawler, or identity-specific routing is permitted.
- Initial deployment budget is Vercel Hobby plus Supabase Free. Supabase/Postgres is the durable source of truth. Redis is deliberately deferred until throughput and latency justify it.
- A redirect must be a single temporary redirect to an allowlisted storefront and preserve `utm_*`, `fbclid`, and other safe query parameters.
- Click-to-order attribution needs a URL-carried signed opaque click token plus storefront capture into cart/order metadata; a central-domain cookie alone cannot survive the cross-domain redirect.
- Revenue targets are optimization goals, never guarantees: conversion timing, AOV variation, duplicate/retried events, cancellations, refunds, payment state, and visitor randomness make exact allocation impossible.

## Premises

- Shopify webhooks are an event source, not a complete ledger. Webhook delivery IDs make ingress idempotent; a scheduled Admin GraphQL reconciliation closes delivery gaps and resolves later status/refund changes.
- “Revenue” will be defined explicitly per campaign as gross paid revenue or net recognized revenue after refunds/cancellations. The MVP begins with paid revenue and visibly reports adjustments.
- Shops that reach a cap become ineligible or receive a configurable exploration allocation; operators can override either behavior.
- The target period, currency handling, and reset timezone must be explicit configuration, never inferred from the server clock.
- The first version must avoid storing customer PII. Store only the minimum order, monetary, event, campaign, and click-linking data needed for allocation and audit.

## Approaches Considered

### Approach A: Database-only minimal router

Extend the current Postgres RPC logic, compute a deficit score during every redirect, and add target fields to stores. This is quick but puts an expensive, write-heavy transaction on the redirect path and becomes fragile under concurrent traffic and webhook bursts.

### Approach B: Production-grade phased control plane and routing plane

Keep Postgres as the durable ledger, separate webhook acceptance from asynchronous processing, and publish a compact allocation snapshot for the redirect path. Begin with Postgres-backed snapshots on free tiers, then add Upstash Redis only when measurements show it is needed. This gives a valuable MVP quickly while retaining a safe path to 50+ stores and high traffic.

### Approach C: Advanced predictive optimizer first

Start with conversion forecasting, Bayesian experimentation, full Meta CAPI, and complex multi-campaign optimization. This may eventually improve efficiency, but it increases cost and failure modes before basic attribution and operational controls are proven.

## Recommended Approach

Choose Approach B. Build a transparent routing product in stages:

1. A durable commerce ledger and configurable store registry.
2. A fast, deterministic redirect path using a precomputed allocation snapshot.
3. A reconciliation and health-control plane so allocation is based on trustworthy revenue.
4. An operator-first control room built with the existing Next.js, shadcn/Radix, and Supabase stack.
5. Redis/queue/CAPI/adaptive optimization as measured upgrades, not free-tier blockers.

## System Shape

```text
Meta ad
  -> https://router.example/r/{campaign-key}
  -> fast selector: validate request -> choose eligible store from allocation snapshot
  -> one 302 redirect with original parameters + signed rt_click token
  -> Shopify storefront captures rt_click into cart/order metadata

Shopify webhooks -> verified webhook ingress -> idempotent event inbox -> worker
                                                              -> orders + adjustments ledger
                                                              -> target-period aggregates
                                                              -> allocation snapshot

Admin dashboard -> store/target/mode controls -> audit log -> allocation refresh
```

The current A/B environment-variable model is replaced with a multi-store installation registry. Each store has encrypted credentials or a secure Shopify app installation, a distinct webhook secret/configuration, an allowlisted destination, independent target/cap/mode, and health state.

## Allocation Policy

The selector only chooses from eligible stores: enabled, healthy, valid destination, below a configured hard cap, and able to accept traffic. For each candidate it uses a periodically refreshed score such as:

```text
target_gap = max(target - recognized_revenue - pending_reservation, 0)
expected_revenue_per_click = smoothed_conversion_rate * smoothed_aov
need_score = target_gap / max(expected_revenue_per_click, floor)
score = need_score × health_factor × priority_weight
```

The system samples from normalized scores rather than always picking the highest score. A minimum exploration share and Bayesian smoothing prevent a newly added or low-traffic store from being starved by noisy conversion data. A store can be set to equal rotation, target balancing, fill-then-skip, priority weighting, or manual allocation. The dashboard always displays the active mode, inputs, current allocation, and the reason it changed.

Pending or authorized orders are reservations with a configurable confidence weight; paid/recognized revenue is the primary target measure. Refunds/cancellations create negative adjustments. Allocation is recomputed after material events and on a short cadence; it is not recomputed with a database lock for every visitor.

## Compliance and Measurement

- Never cloak: all stores must be legitimate, accessible destinations with the same advertised offer, and the router must not detect reviewers, bots, Meta IPs, user agents, or geography to show a different experience.
- Preserve source parameters exactly where safe and append an opaque, signed, short-lived click token. Do not put customer data in URLs.
- The landing storefront, not an invisible redirect page, runs the browser Meta Pixel. Use a shared or intentionally mapped Meta dataset only after confirming account ownership and consent requirements.
- Server-side Conversions API is added after canonical purchase data exists. Browser Pixel and CAPI purchase events use the same event name and `event_id` for deduplication; send consent-appropriate, minimized data only.
- Retain routing and attribution records for a defined business period; minimize protected Shopify customer data and document a deletion/export process.

## MVP Success Criteria

- Configure 3–10 stores with independent targets, modes, caps, and activation state.
- Public routing stays one-hop, avoids loopable destinations, preserves campaign parameters, and supplies a signed click token.
- Shopify deliveries are HMAC-verified, acknowledged quickly, deduplicated, processed asynchronously, and reconciled on a schedule.
- The operator can see traffic, orders, paid revenue, refunds/adjustments, conversion rate, AOV, target attainment, allocation, health, and audit history by store and target period.
- A store can be paused immediately; an unhealthy store is excluded and a safe fallback is selected.
- Target-balancing allocation converges toward targets in simulation and real campaign observation, while clearly reporting that exact per-store revenue cannot be guaranteed.

## Open Questions

- Exact business timezone, currency policy, and whether targets use gross paid or net-after-refund revenue.
- Expected peak redirects and orders per minute, which determine when Redis and a managed queue become necessary.
- Whether each Shopify store can install a custom app/theme extension to carry the click token into the final order.
- Meta Business/Dataset ownership, consent requirements by sales geography, and final policy review inside the active ad account.

## Dependencies

- Shopify app credentials/scopes and verified webhook subscriptions per store.
- A custom router domain and DNS/HTTPS configuration.
- Supabase authentication/RLS and production backup/retention decisions before handling real campaign data.
- A policy/compliance review before production ads run.

## The Assignment

Before implementation begins, list every participating Shopify store with its domain, desired daily target, timezone/currency, whether it should stop at its cap, and the intended fallback priority. This becomes the first import sheet and exposes operational edge cases before traffic is live.
